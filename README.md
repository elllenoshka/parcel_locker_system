# C11 «Поштомати»

**Спільний навчальний проєкт з дисциплін:**
- «Обмін даними у Web-застосунках» (Web);
- «Розподілені та паралельні обчислення» (DPC).

Проєкт присвячений розробленню системи бронювання комірок поштоматів, оброблення посилок та аналізу завантаженості мережі поштоматів.

## 2. Проєкт

### 2.1. Призначення системи

Метою проєкту є розроблення платформи для роботи з мережею поштоматів.

Система має дозволяти відправникам переглядати доступні поштомати, бронювати комірки відповідного розміру та відправляти посилки. Отримувачі зможуть отримувати повідомлення й забирати посилки за спеціальним кодом.

Окрема частина системи відповідатиме за оброблення запитів на закладання посилок, паралельні обчислення, аналіз завантаженості поштоматів та координацію розподілу комірок.

### 2.2. Ролі користувачів

- **Відправник** — переглядає поштомати, бронює комірки, керує власними відправленнями.
- **Отримувач** — отримує сповіщення та забирає адресовані йому посилки.
- **Персонал (staff)** — виконує службові операції, зокрема виведення несправних комірок з експлуатації.

### 2.3. Основний сценарій

1. Відправник вибирає поштомат і розмір комірки (S, M або L).
2. Web-сервіс перевіряє наявність вільної комірки.
3. Комірка бронюється на 24 години.
4. Відправник закладає посилку до заброньованої комірки.
5. DPC обробляє закладання, використовуючи саме заброньовану комірку.
6. Система формує події та сповіщення.
7. Отримувач отримує код і забирає посилку.
8. Комірка знову стає доступною.

### 2.4. Стани посилки

Передбачені переходи станів:

- `held → dropped → picked`
- `held → dropped → returned`
- `held → expired`
- `held → cancelled`

Позначення:

- `held` — комірка заброньована;
- `dropped` — посилку закладено;
- `picked` — посилку отримано;
- `returned` — посилку повернено;
- `expired` — строк бронювання завершився;
- `cancelled` — бронювання скасовано.

### 2.5. Основні інваріанти

Система повинна забезпечувати такі правила:

1. Одна комірка не може одночасно містити більше однієї посилки.
2. Розмір посилки не може перевищувати розмір комірки.
3. Кількість зайнятих комірок певного розміру не може перевищувати їх загальну кількість.
4. Повторне виконання операції з тим самим предметним ключем не повинно створювати повторного ефекту.
5. Закладання вже заброньованої через Web посилки не повинно займати додаткову комірку в DPC.

### 2.6. Предметні дані

Для Web-частини передбачені основні сутності:

| Сутність | Призначення |
|---|---|
| `locker` | Інформація про поштомат, адресу та часову зону |
| `cell` | Комірка, її розмір, стан і версія |
| `parcel` | Посилка, відправник, отримувач, розмір, вага та статус |

Для DPC передбачено ресурс `locker_cells` із полями `locker_id`, `size`, `total`, `used`.

Спільні ідентифікатори двох частин: `locker_id` та `parcel_id`.

### 2.7. Обчислення та аналітика DPC

DPC виконує паралельне чисельне інтегрування функції інтенсивності надходження посилок:

**λ(t) = A · t · (T − t), де T = 14.**

Результат інтегрування використовується для оцінювання кількості посилок за день і планування необхідної кількості комірок.

Також передбачається:

- пакетна аналітика завантаженості поштоматів за розмірами комірок і днями;
- аналіз історії посилок у форматі Parquet;
- оброблення подій закладання та отримання посилок;
- погодинне агрегування подій;
- врахування запізнілих подій до 10 хвилин;
- відновлення обчислень після відмов.

## 3. Архітектура

Проєкт складається з двох взаємопов'язаних частин — Web та DPC, які працюють зі спільною предметною областю.

### 3.1. Web

Web-частина відповідає за:

- взаємодію з користувачами;
- бронювання комірок;
- керування посилками та їхніми станами;
- автентифікацію й авторизацію;
- асинхронні операції із зовнішньою системою;
- публікацію подій;
- доставку сповіщень через WebSocket.

Для реалізації серверної частини обрано Java та Spring Boot.

### 3.2. DPC

DPC-частина відповідає за:

- приймання запитів на закладання посилок;
- оброблення запитів через обмежену чергу;
- паралельне виконання обчислень;
- розподілені задачі Ray;
- пакетну обробку Spark;
- потокову обробку подій Kafka;
- координацію розподільників комірок через etcd.

Для основного API обрано Java та Spring Boot. Обчислювальні компоненти будуть організовані відповідно до вимог лабораторних робіт.

### 3.3. Спільна інфраструктура

Заплановані технології:

| Технологія | Призначення |
|---|---|
| Java, Spring Boot | Серверні застосунки |
| PostgreSQL | Збереження предметних даних |
| Docker Compose | Запуск компонентів системи |
| nginx | Балансування запитів Web |
| Kafka | Обмін подіями |
| Ray | Розподілене виконання задач |
| Apache Spark | Пакетна та потокова аналітика |
| etcd | Координація виконавців |
| WebSocket | Сповіщення користувачів |

### 3.4. Розподіл відповідальності

Web відповідає за бронювання комірки для відправника.

DPC відповідає за оброблення закладання посилки та, за відсутності бронювання, призначення комірки через координатора.

Якщо комірку вже заброньовано через Web, DPC використовує цю саму комірку за `parcel_id`.

Спільні операції повинні зберігати інваріанти та не спричиняти подвійного зайняття ресурсу.

Деталі взаємодії, транзакцій і передавання подій будуть уточнюватися під час реалізації лабораторних робіт.

## 7. Досліди

Для перевірки правильності реалізації передбачається проведення контрольованих дослідів.

Основні заплановані сценарії:

- одночасне бронювання останньої доступної комірки;
